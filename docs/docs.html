Variables & types

Variables are PHP-style: start with $, no declaration keyword, inferred types. Add an explicit type after the name when you want one.

$count = 5;                  // inferred int
$pi = 3.14159;               // float
$ok = true;                  // bool
$who = "Ada";              // string

$count: int = 5;             // pinned types
$rate: float = 0.19;
$name: string = "Ann";
$flag: bool = false;

$items = [1, 2, 3];          // list array
$user = ["name" => "Ada",  // map array (string keys)
         "lang" => "HolyPHP"];

i128 is a native 128-bit signed integer. It widens from int and the sized integer spellings implicitly, in assignments, arguments, returns and mixed arithmetic (the result stays i128). Narrowing back to int needs an explicit cast; (i128) itself converts from int, float, string and other integers. Arithmetic, comparisons, the spaceship operator, bit operations and shifts all work; / and % are integer division and modulo (unlike int / int, which yields a float), and dividing by zero throws. Overflow wraps like int.

$big = (i128)1 << 100;            // 1267650600228229401496703205376
echo $big * 2;                  // 2535301200456458802993406410752
echo strval($big);              // full decimal value
$back = (i128)"-77";            // from a string
$narrow = (int)$big;            // only an explicit cast narrows

An i128 does not fit into an array, a map, a mixed slot or a closure (those hold a 64-bit runtime value). Storing one there is a compile error rather than a silent truncation: convert with (int) or strval() first. echo, concatenation, templates, strval(), print_r, var_dump and json_encode (as a JSON number) print the full value.

Functions

Fully typed signatures with optional parameters and defaults. Untyped functions are inferred like scripts.

function greet(string $who): string {
    return "Hi, {$who}!";
}

function pow2(float $base, int $exp = 2): float {
    return $base ** $exp;
}

// by-reference parameter (a mutable borrow)
function bump(int &$r): void { $r += 1; }

$n = 41;
bump($n);        // $n === 42

An &$r parameter aliases the caller's variable: the callee writes through it and the call site sees the new value. The argument must be a variable the compiler can alias, and it may live in any of the shapes a variable takes here — a local, a global, a slot a closure captured with use (&$x), or another by-reference parameter.

function anonymize(mixed &$who): void { $who = "nobody"; }

$user = "Elias";
$seen = function() use (&$user): void { anonymize($user); };  // boxed capture
$seen();
echo $user;      // nobody

function total(array &$bag): void { $bag[] = 3; }

$bag = [1, 2];
total($bag);     // $bag === [1, 2, 3]
What is not aliased: a by-reference argument has to be a variable (“bump(1 + 1)” is an error, not a silent copy), a closure cannot declare one (its arguments arrive boxed — capture with use (&$x) instead), and a by-reference parameter cannot itself be captured by reference, since that would need a write-back the compiler does not emit yet. Each of those is a compile error naming the line, never a wrong answer.

Classes & OOP

Visibility is explicit: pub (public), private, static for fields. Methods inherit PHP-style; constructors may be inherited too.

class Counter {
    pub int $count = 0;          // field with default
    private $secret = "s";

    pub function __construct(int $start = 0) {
        $this->count = $start;
    }
    pub function bump(): void {
        $this->count += 1;
    }
    pub function get(): int {
        return $this->count;
    }
}

$c = new Counter(10);
$c->bump();
echo $c->get();      // 11
class Animal {
    pub function speak(): string { return "..."; }
}
class Dog extends Animal {
    pub function speak(): string { return "Woof!"; }
}
echo (new Dog())->speak();   // "Woof!" — dynamic dispatch

Closures & captures

Closures capture PHP-style with use. By-value copies by default; use (&$x) captures by reference — the variable lives in a heap box shared with the outer scope.

$base = 100;
$addBase = function(int $x) use ($base): int {   // by value
    return $base + $x;
};

$clicks = 0;
$onClick = function() use (&$clicks): void {     // by reference
    $clicks = $clicks + 1;                       // outer $clicks changes
};
$onClick(); $onClick();
echo $clicks;    // 2
Why it's safe: the compiler boxes the captured variable and forces it to mixed, so the same slot is shared — no dangling pointers, no data races, verified by hphp check.

Exceptions

try {
    throw "boom";
} catch (string $e) {
    echo "caught: {$e}";
} finally {
    echo "always runs";
}

throw accepts a value (strings today, Exception objects too). Handlers are invoked through a setjmp-free architecture — the runtime runs each protected block as a helper, so no volatile tricks appear in generated code and -O2 is safe.

Memory model

HolyPHP checks ownership and supported borrow patterns at compile time. The checker is still a subset of Rust's borrow checker; dynamic values, aliases and unsafe code have additional limits.

// borrow checker at compile time:
function laenge(string $text): int {     // takes an immutable borrow
    return strlen($text);
}
$w = "borrowed";
echo laenge($w);        // owner keeps $w

// this is a compile ERROR (two mutable borrows):
// function bump(int &$r): void { $r += 1; }
// bump(&$n); bump(&$n); ...  => rejected by hphp check
unsafe {
    $geheim: int = 42;
    $zeiger: &int = &$geheim;      // raw pointer
    echo "deref = " . (*$zeiger);
}
unsafe: raw pointer operations need an unsafe block. The compiler cannot guarantee memory safety for code that uses raw pointers or escapes the supported borrow rules.

Use declare(enforce_memory_safety=1); at the start of a file to make unsafe blocks and calls to builtins marked unsafe compile errors. The declaration applies to the whole file, and the borrow checker analyzes the file's script and functions. Both this mode and ordinary code use the same reference-counted value representation.

Runtime memory: generated owners retain and release strings, arrays, closures, and class instances. Arrays detach on mutation when shared. Strong cycles across objects, arrays, and closures are collected automatically. A weak property does not keep its target alive; it reads as a nullable value and becomes null after collection. See the memory model guide for ownership rules and remaining limits.

Runtime cost: before a program starts a thread, reference counts use a single-thread path and cycle-collector registry operations avoid the mutex. Starting a thread switches those operations to synchronized mode. Generated string-literal sites cache their handle after first use, and owner cleanup registrations reuse a per-thread buffer. In safety mode, parameters used only by read-only builtins such as count(), array_sum(), and strlen(), or forwarded to another proven borrowing parameter, can omit the call-boundary retain/release pair. Unknown calls, writes, returns, stores, methods, and closures keep the normal RC path. A function-local array made from scalar literals also uses a short-lived arena when every use is read-only; returning, storing, or mutating it keeps normal ownership. In canonical counted loops, the same proof can also remove array index checks when the body only passes the stable array to a proven borrower. Safety mode also uses reusable iteration regions for local scalar arrays and strings whose uses stay inside the loop, including method bodies. Calls on concrete class receivers may borrow direct local arguments when every reachable override proves the parameter read-only and nonescaping. Interface or unknown dispatch keeps normal reference counting.

Unsafe pointers: raw addresses are integers outside the managed-object reference-count path. memset() and memcpy() return their input address; stream_recv() copies data out of reusable io_uring buffers before returning an owned string. Builtin temporary cleanup respects borrowed results and immortal string literals.

Indexing: array-list and string reads check their bounds at runtime. An out-of-range read raises a catchable error ("Array index out of bounds" or "String index out of bounds"). Map lookups for absent keys continue to return null. The compiler removes checks in a canonical counted loop when it proves the array and induction variable are stable; in safety mode the body may also pass the array to a proven borrower; other reads retain runtime checks. foreach uses a runtime iterator. array_sum() promotes to a float if adding integer elements would overflow int64.

Threads: captured values and channel payloads move across the thread boundary, so later use of a moved source is a compile error. Immutable scalar and string values may be shared; arrays and maps move when their contents are safe value types and keep copy-on-write behavior. Ordinary mutable objects cannot be sent through channels. Known closures are checked at the boundary, including indirect callbacks typed as thread_callable. The bundled Thread and Pool wrappers use the same checks. See the memory model guide for the proof limits.

Imports & the stdlib

Libraries ship inside the compiler binary — import finds them with no files on disk. A spec without an extension names a library or package; with .hphp it means a file next to the importing source.

import "ui";        // desktop GUI toolkit (embedded)
import "websocket"; // RFC 6455 server (embedded)
import "async";     // event loop + HTTP (embedded)
import "thread";    // OS threads + channels (embedded)
import "helpers";     // helpers.hphp next to this file

Strings

Immutable and refcounted; interpolation is compile-time parsed into concat calls.

$name = "Ada";
echo "Hi {$name}, you have " . (3 + 4) . " new messages";

$s = "Hello";
$s .= " World";          // append (rebuilt behind the scenes)

Arrays & maps

One type for both: lists keep insertion order; assigning a string key or a non-sequential int key promotes to a keyed map (exactly PHP's semantics).

$nums = [5, 3, 8, 1, 9];
$nums[] = 7;                 // append
sort($nums);                 // in place
echo $nums[0];               // 1

$m = [];
$m[1] = "a";                 // key 1 is remembered
$m["name"] = "Ada";        // becomes a keyed map
foreach ($m as $k => $v) {
    echo "{$k} => {$v}";   // 1 => a, then name => Ada
}

$a = [1, 2, 3];
$b = $a;                     // COW: shares until one writes
$b[0] = 99;                  // clones now; $a unchanged

First database

sqlite_open() opens an existing file; it deliberately does not create one, so a typo in the path cannot silently produce an empty database. touch() creates the file, then SQL does the rest.

Handles are raw pointers. A database or statement handle is SQLite's own pointer widened to an integer, and bt_* hands out payload addresses. The compiler therefore requires these calls inside unsafe { }: sqlite_open, sqlite_open_vfs, sqlite_prepare, bt_open, bt_root, bt_payload_ptr, bt_payload_pin, bt_multi_seek, bt_tail, bt_read, bt_col_off and bt_col_len. Nothing checks the integer for you; a stale handle is a dangling pointer.

The B-tree path

bt_* is what the bundled challenge server uses for its hottest reads: skip SQLite's virtual machine, seek the table B-tree by rowid or the index B-tree by key, decode the record bytes in place. It is a driver primitive, not a second SQL engine — the caller owns every buffer, page pin and cursor lifetime.

$db = sqlite_open($path);
$users = bt_open($db, "users", 0);          // table cursor
$by_name = bt_open($db, "users_name_idx", 1); // index cursor

// table: move to rowid 7 and decode the record at the cursor
if (bt_seek($users, 7) == 1) {
    $rowid = bt_rowid($users);
    $cols  = bt_cols($users);               // decode this record once
    $off   = bt_col_off(1);                 // second column, byte offset
    $len   = bt_col_len(1);
    $size  = bt_payload_size($users);       // bytes available on this page
}

// index: how many entries start with key 3, and a histogram for 1..20
$likes = bt_count_key($by_name, 3);
$hist  = iarr_new(20);
bt_count_range($by_name, 1, 20, $hist);

bt_close($users);
bt_close($by_name);
sqlite_close($db);

HolyPHP evaluates call arguments right-to-left, so bt_cols() and the column accessors must be separate statements — the same rule the challenge server follows.

WAL checkpoints

A write-heavy program with its own event loop can move SQLite's passive checkpointing to a worker thread, so a large WAL never stalls request handling. The worker uses a second connection to the same file.

$db = sqlite_open($path);
sqlite_exec($db, "PRAGMA journal_mode = WAL");
sqlite_exec($db, "PRAGMA wal_autocheckpoint = 0");
sqlite_bg_checkpoint_start($db, $path, 4096, 4);   // frames, max hold in ms

for (;;) {
    // serve requests ...
    sqlite_bg_checkpoint_tick($db);                // once per poll cycle
    if (sqlite_bg_checkpoint_hold($db)) {
        // commits are overtaking the copy: hold writes for a moment
    }
}
// sqlite_close($db) also stops the worker

sqlite_bg_checkpoint_start refuses when SQLite was built without thread safety or a worker is already running. On Windows the worker stays off and these three calls report false; everything else works the same.

What gets linked, and which SQLite

The vendored amalgamation lives in third_party/sqlite/ (public domain; version, checksums and the compile options are documented in its README). scripts/build.sh compiles it once per platform with src/hp_btree.c appended, because the B-tree builtins use SQLite's private structures, and embeds the static archive in the compiler. At build time the compiler writes it next to the generated program and links it only for programs that call sqlite_* or bt_*.

VariableEffect
HPHP_SQLITE_LIBlink this archive instead of the embedded one (a system or debug build)
HPHP_SQLITE_VFSVFS name; the challenge uses unix-excl so the process holds the database lock itself
HPHP_SQLITE_WAL_COALESCE1: write each commit's WAL frames with one pwrite

On Linux a bt_* program needs no libsqlite3.so: the archive is static. A plain program links neither SQLite nor io_uring.

hphp check file.hphpType + borrow check only. Fastest feedback loop; prints OK (types and borrows check) or precise diagnostics with line numbers.
hphp run file.hphpCompile to a temp binary and execute it. Perfect for scripts and quick iteration.
hphp build file.hphp -o app.exeProduce a standalone executable. Ships with the runtime linked in — no dependencies on the target machine.
hphp emit file.hphpPrint the generated C (for the curious and the debugger-inclined).
hphp create [name]New project folder from a template (console, web, lib, empty). Asks a few questions in a terminal; --yes and the options from hphp create --help for scripts.
hphp run / build / checkWithout a file, inside a project: use the entry from hphp.yaml. hphp build then writes build/<name>.
hphp install [pkg[@version]]In a project: install everything from hphp.yaml into .hphp/packages/ (keeping hphp.lock), or add one dependency (--dev for require-dev, a folder such as ../mylib for a local package). Outside a project: install a package for your user, as before.
hphp update [pkg]Move dependencies to the newest version their constraint allows and rewrite hphp.lock.
hphp remove pkgDrop a dependency, its folder and whatever only it needed.
hphp depsList the locked dependencies and where they came from.
hphp test [filter] [-v]Run every tests/*.hphp of the project; a test passes when it exits 0.
hphp pkg ...Package manager: init, check, pack, publish, install, remove, search, registry, list, home. See the Packages page.

Typical workflow

hphp check app.hphp          # instant: types + borrows
hphp run app.hphp            # quick run
hphp build app.hphp -o app.exe   # ship it

Editor support

A VS Code extension lives in extension/hphp: syntax highlighting, completions for all 305 builtins (generated from the compiler's own table), hover signatures, and live diagnostics that run hphp check as you type.

Under the hood

The pipeline is: lexer → recursive-descent parser → semantic analysis (types, borrows, ownership) → C codegen → cc + ld. The runtime (values, strings, COW arrays, exceptions, Win32 UI, sockets) is embedded in the compiler binary and extracted at build time, compiled with your local gcc, and linked statically — which is why output exes are a few hundred KB and start instantly.

Projects & packages

HolyPHP ships with its own package manager. Packages are plain folders of .hphp files described by an hphp.json manifest, packed into a portable .hpx archive, and shared through a registry — which is itself a HolyPHP program (registry/server.hphp, ~250 lines).

Projects: hphp create

A project is a folder with an hphp.yaml. Its dependencies are installed into the project's own .hphp/packages/ folder and pinned in hphp.lock, so every project keeps its own versions and a fresh clone gets exactly the same ones with one command.

hphp create                       # asks: name, template, description, author, license, ...
hphp create shop -t web --yes     # no questions: web template, defaults

cd shop
hphp install                      # everything in hphp.yaml (keeps hphp.lock)
hphp install websocket            # add a dependency (pins "^x.y")
hphp install thread@^1.0          # ... with a version constraint
hphp install phpunit_lite --dev   # only for development (require-dev)
hphp install ../mylib             # a local package folder (path:../mylib)
hphp update                       # newest allowed versions, rewrites hphp.lock
hphp update websocket             # just one package
hphp remove websocket             # drop it (and what only it needed)
hphp deps                         # what is installed, from where
hphp run                          # runs the entry from hphp.yaml
hphp test                         # runs tests/*.hphp (a test passes when it exits 0)
hphp build                        # writes build/shop(.exe)

Templates: console (input + colored output), web (HTTP server with routes on the async library), lib (a package with tests, ready for hphp pkg publish) and empty. hphp create --help lists the options for scripts and CI (--template, --description, --author, --license, --safe, --no-git, --yes).

Layout

shop/
  hphp.yaml            name, version, entry, require, require-dev
  hphp.lock            exact versions + checksums - commit it
  src/main.hphp        the entry file
  src/routes.hphp
  tests/routes_test.hphp
  .hphp/packages/      installed dependencies - not committed (.gitignore)
  build/               hphp build output

The project file: hphp.yaml

# HolyPHP project file
name: shop
version: 0.1.0
type: project            # or: library
description: A HolyPHP web server.
entry: src/main.hphp
author: Ada
license: MIT

require:
  async: "^1.0"          # 1.x from 1.0
  websocket: "~1.2"      # 1.2.x
  mylib: "path:../mylib" # a local folder

require-dev: {}

Version constraints: "*" any, "1.2.3" exactly, "1.2" any 1.2.x, "^1.2" 1.2 up to (not including) 2.0, "~1.2" 1.2.x, ">=1.0 <2.0" a range, "^1.0 || ^2.0" either. Quote them: * and ^ mean something else in plain YAML. The file is a small YAML subset: key: value, one level of nested name: "version" lines, {} for an empty map, and # comments.

import "async"; looks in the importing file's project (.hphp/packages/async/) before the per-user package home and the libraries bundled in the compiler. Packages come from the registry; when it is unreachable or does not have them, from the libraries bundled in hphp (works offline). The registry serves the newest version of a package only, so a constraint it cannot meet fails with a clear message instead of installing something else. hphp.lock records an FNV-1a checksum of every archive; a package that changed under the same version number stops the install.

Older projects with an hphp.json keep working; when a folder has both, hphp.yaml wins. hphp pkg pack and hphp pkg publish read hphp.yaml and add a generated hphp.json to the archive, so registries and older clients understand it; .hphp/, .git/ and build/ are left out.

Official and community packages

Every package is one of three kinds; hphp deps and hphp.lock show which (trust:).

KindWhere it comes fromOn install
officialthe libraries bundled with hphpinstalled from the compiler itself, never from a registry: a registry package can not take an official name, and the registry refuses to publish one
communitya registry or a .hpx filereviewed first: you see where it is from, its author (as it claims), and what its code can do, then answer y to install
localpath:../mylibyour own code, installed without asking
$ hphp install leftpad

  ! community package: leftpad 1.2.0
    from:    registry http://hphp.ch:8930
    author:  someone   (as written in its manifest, not verified)
    files:   2 (1 HolyPHP source)
    it can:  run shell commands         leftpad.hphp:4  shell_exec("curl ... | sh");
             write or delete files      leftpad.hphp:5  unlink("/tmp/x");

    Official libraries ship with hphp and are reviewed with it. Community
    packages are written by anyone: install only what you trust. The list
    above is a hint from reading the source, not a guarantee.

  Install leftpad 1.2.0? [y/N]

The review looks for shell commands, file writes and deletes, network connections, unsafe code, native libraries (FFI), environment changes and file reads. Answering anything but y installs nothing and leaves hphp.yaml as it was. Once accepted, the package's checksum is in hphp.lock: a fresh clone runs hphp install without asking again, and a package that changed under the same version asks again. Without a terminal (CI) nothing is installed unless you pass --trust: hphp install --trust.

Quick start

hphp pkg init                     # create hphp.json skeleton in this folder
hphp pkg check                    # typecheck the package's entry file
hphp pkg pack                     # build name-version.hpx into your pkg cache
hphp pkg publish                  # pack + upload to the configured registry
hphp pkg install mathx            # download + unpack into $HPHP_HOME/packages
hphp pkg remove mathx             # uninstall (alias: uninstall)
hphp pkg list                     # show installed packages
hphp pkg search clamp             # search the registry (falls back to local)
hphp pkg registry http://localhost:8930   # point the client at a registry
hphp pkg home                     # print the package home directory

The manifest: hphp.json

{
  "name": "mathx",
  "version": "1.0.0",
  "description": "tiny math helpers",
  "entry": "mathx.hphp",
  "author": "you"
}

entry is what hphp pkg check typechecks (defaults to <name>.hphp). Packing walks the whole package folder, so every file in it ships in the archive.

Using an installed package

hphp pkg install mathx unpacks into $HPHP_HOME/packages/mathx/. The compiler's import resolution then searches:

  1. the importing file's directory (project-local files, e.g. import "mymod" → mymod.hphp)
  2. $HPHP_HOME/packages/<name>/ (installed packages)
  3. libraries embedded in the compiler (works offline)
// app.hphp — after: hphp pkg install mathx
import "mathx";

echo "clamped: " . clampi(42, 0, 10);   // 10

Run your own registry

The registry is a normal HolyPHP program using the socket builtins (stream_socket_server, stream_ready, stream_recv, stream_send). It serves a browsable index, ?q= search, package downloads under /pkg/<name>, and accepts uploads via POST /publish.

cd registry
../hphp.exe run server.hphp          # listens on http://localhost:8930
HPHP_HOME=../store ../hphp.exe run server.hphp --store /var/hphp-packages

The public community registry runs at http://hphp.ch:8930 and is the compiled-in default of the released installers — hphp pkg install thread works out of the box.

Packages live as <name>.hpx + <name>.json metadata in the store directory, so a registry can be backed up, synced, or moved to another machine by copying one folder. Point clients at it from any device:

hphp pkg registry http://your-server:8930

End-to-end walkthrough

# 1. author
mkdir mathx && cd mathx && hphp pkg init
#    ... edit mathx.hphp and hphp.json ...
hphp pkg check                        # types + borrows

# 2. share (machine A)
hphp pkg publish                      # -> uploaded to the registry

# 3. consume (machine B, same registry)
hphp pkg registry http://your-server:8930
hphp pkg install mathx
hphp run app.hphp                     # import "mathx" just works

How it works under the hood

  • .hpx format — a trivial tar-like container: repeated name  size\n headers followed by raw payload, terminated by HPHX1. Human-readable, streamable, no dependencies.
  • Package home — HPHP_HOME (defaults to a per-user folder): cache/ for downloaded archives, packages/ for installed code, registry_url for the configured server.
  • Publish — the client packs, then POSTs the archive as application/octet-stream; the server validates the embedded manifest and stores it.
  • Install — the client downloads, unpacks to a temp dir, validates the manifest, then moves it into packages/<name>.

HolyIDE

HolyIDE: an editor and a workbench for HolyPHP, written in HolyPHP on top of the html library. Its package (packages/lib/ide) is the whole IDE except the window, which is why all of it is tested without one.

a program written in HolyPHP text buffer + undo syntax + completions explorer, tabs, palette runs hphp from the IDE

Two halves, one import

FileWhat it is
ide/editor.hphpthe document model: lines, caret and selection, editing keys, undo/redo, the syntax tokenizer, the completion vocabulary
ide/workbench.hphpthe chrome: explorer tree, tabs, code pane, terminal and problems panel, status bar, command palette, key table, runner — rendered to HTML and handed to an HtmlView
holyide/holyide.hphpthe window: one canvas, forwarded events, a frame timer. Not part of the library — it is the ~140-line app around it.

The editor on its own

The buffer, the caret and the editing operations have no idea a screen exists. Load a file, type into it, undo, save — no window anywhere.

import "ide";

$ed = new IdeEditor();
$ed->load("holyide/holyide.hphp");
$ed->move("docstart", false);
$ed->type_char("/");
$ed->type_char("/");
echo substr($ed->line(0), 0, 20);   // //// ==== ...
$ed->undo_step();
echo $ed->status();         // undo/redo state, position, tokens

echo $ed->word_at_cursor();
foreach ($ed->completions("str", 8) as $w) { echo $w; }

The workbench, driven headlessly

The workbench owns state and renders it to HTML. A test — or your own tool — builds one with no canvas (0), opens a folder, lays the document out with ensure() and then reads boxes, clicks and key results. tests/positive/ide_workbench.hphp does exactly that.

import "ide";

$wb = new IdeWorkbench(0, 1180, 760, html_theme_dark());
$wb->open_root(".");
$wb->open("lib/ide/workbench.hphp");
$wb->ensure();                          // parse, style, lay out (no ink)

echo $wb->ed()->line_count() . " lines";
echo "code pane: " . $wb->ed_rows() . " rows x " . $wb->ed_cols() . " cols";

$wb->key(80, "", 1);                    // Ctrl+P: the file palette
$wb->key(0, "work", 0);                 // type a query
$wb->key(13, "", 0);                    // Enter: open the first match

Opening it in a window

hphp run holyide/holyide.hphp                 # the current folder
hphp run holyide/holyide.hphp ../my-project   # another one
hphp build holyide/holyide.hphp -o holyide.exe

The app forwards canvas events to key() / mouse(), pumps the running program from a frame timer, follows window resizes and acts on the one string that needs a window: "quit".

What the mouse does

  • A click in the code puts the caret where the pointer is; the gutter picks the whole line. Hold the button and drag to select.
  • A double click selects the word under the pointer.
  • The explorer folds: clicking a folder shows or hides what is in it, clicking a file opens it in a tab.
  • The 5px strip between the explorer and the editor, and between the editor and the panel, is a grip: drag it and that pane changes size. Hovering lights it up, so it can be found.
  • The wheel moves the code one line a notch - it is a scroll, not a jump - and two rows a notch in the explorer.

What runs a file

Ctrl+R starts hphp run <file> through the runtime's proc_* pipe API, in the file's own folder. Output appears in the terminal panel; a failing compile is parsed into the problems list, and clicking a problem opens the file at its line.

The panel is also a terminal, in the small sense: a command line at the bottom, Ctrl+` or a click to focus it, Enter to run through cmd /c in the project folder, Up/Down for history, Tab to hand the keyboard back to the editor. It is a command line over pipes, not a TTY - no interactive prompt, no colours, no full-screen programs.

Status

The workbench is complete and tested headlessly: 100+ assertions cover the editor, the layout numbers, the palette ranking, tabs, the runner and the draw list. The window app exists and passes a pixel self-check (holyide --selftest).
